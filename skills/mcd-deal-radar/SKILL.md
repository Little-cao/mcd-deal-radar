# 麦当劳订阅雷达（mcd-deal-radar）

## 这个 skill 是什么

一个**纯对话 + MCP 工具驱动**的 skill：**不依赖任何本地脚本，也不绑定特定平台**。
智能体在对话中直接调用麦当劳 MCP 工具，完成四件事：

1. **引导配置**——**手把手带小白用户**完成「申请 Token → 配置 MCP → 建定时任务」（见「第零步」）；
2. **订阅**——理解用户「想订阅什么」以及「多久检查一次」，生成一条**宿主智能体平台的定时任务**；
3. **检查**——按用户设定的频率（默认每天 12:00 / 24:00）由定时任务唤醒智能体，调用 MCP 取数并比对；
4. **推送**——发现新变化时，由智能体把整理好的摘要发到用户邮箱。

此外还支持**定时点餐**（见「场景 E」）：按用户设定的周期（工作日 / 每天 / 指定星期几 /
每月某日 / 一次性等）到点自动选好固定套餐、生成订单，
把付款入口（麦当劳 App 链接）推给用户，**由用户自己在麦当劳 App 内付款**。

它可以**被其他技能调用**：任何技能只要识别到「订阅麦当劳优惠 / 查询麦当劳套餐」的意图，
即可转入本 skill。

> ⚡ **设计原则：取数用 MCP 工具，不用自建脚本。**
> 麦当劳 MCP 由**宿主智能体平台**（WorkBuddy、Hermes 等）的连接器统一接入，智能体直接调用即可；
> 用户订阅了什么，**由宿主平台的定时任务自带**（每条订阅 = 一个定时任务），
> 无需额外的存储或脚本。
>
> **平台无关性**：本 skill 不假设任何特定平台。凡具备以下两项能力的智能体平台均可运行本 skill——
> ① 能连接麦当劳 MCP Server；② 具备定时任务（Scheduler / Cron / 自动化任务）能力。
> 例如 **WorkBuddy**、**Hermes**、或其他同类平台，按各自平台的定时任务机制落地即可。
>
> 🎯 **面向小白用户**：**假设用户什么都不懂**——他不会申请 Token、不会配 MCP、不会建定时任务。
> 本 skill 的职责是**全程手把手引导**，把「申请 Token → 配置 MCP → 订阅 → 建定时任务」
> 整条链路带用户走完（见下方「第零步」），而不是丢个链接让用户自己摸索。

## 第零步：环境准备与引导式配置（最重要）

**在用户第一次使用本 skill 时，先判断环境是否就绪；未就绪则主动引导用户一步步完成。**
用户只需「跟着做」，不需要理解 MCP / Token / 定时任务这些概念。

### 0.1 判断环境状态

智能体先做一次**静默探测**（不打扰用户）：

- 尝试调用一个轻量的麦当劳 MCP 工具（如 `now-time-info`）；
- **能调通** → 环境已就绪，直接进入用户的实际需求（场景 A/B）；
- **调不通 / 找不到 mcd-mcp 工具** → 说明麦当劳 MCP 尚未配置，进入 0.2 引导流程。

### 0.2 引导用户申请 Token（用户只需做这一件事）

用**大白话**、像朋友发微信那样说话，别甩术语、别念文档。

**开场**（先解释为什么、再说怎么做，让用户有底）：

> 「这个小功能需要麦当劳官方给咱们一把『钥匙』，有了它我才能帮你查菜单和优惠。
> 拿钥匙很简单，你照着点几下，1 分钟就搞定，我在这儿等你～」

**然后给步骤**（编号、短句、每步只一件事）：

> 1. 手机或电脑打开这个网址：**https://open.mcd.cn/mcp/doc**
> 2. 点右上角的 **「登录」**，填手机号、收个验证码登进去；
> 3. 登进去以后，右上角的「登录」两个字会变成 **「控制台」**，点它；
> 4. 弹出来的小窗口里有个 **「激活」**，点一下；
> 5. 会让你同意一个协议，点 **「同意」** 就行；
> 6. 这时候你会看到一大串字母数字，那串 **就是钥匙**——点旁边的 **「复制」**，
>    然后直接**粘贴发给我**，剩下的交给我来处理 ✅

**用户卡住怎么办**（智能体主动接话，别干等）：

- 用户可以**一次只做一步**，做完回你一声，你再给下一步——不用一口气全做完；
- 用户问「钥匙（Token）是什么」→ 打个比方就够：「它就像麦当劳给咱们发的一张会员卡，
  有了它我才能帮你查有哪些套餐、有啥优惠。它只跟麦当劳有关，不会动到你的钱。」
  不要展开讲 MCP、鉴权这些技术词；
- 用户问「安全吗 / 会不会泄露」→ 安抚：「这串钥匙只用来让我查麦当劳的信息，
  我拿到后只在这台设备上配一次，不会存下来、也不会发给别人。」
- 用户在手机上进不去 / 点不到某个按钮 → 给替代说法（「右上角有三个点或头像，
  点开找『控制台』」），或者让用户换个浏览器再试；
- 用户嫌麻烦 → 「理解～就这一回，配好以后你再也不用管了，有优惠我主动喊你。」

**智能体注意**：

- 全程口语，**别出现 Token / MCP / 连接器 这类词**，一律用「钥匙」「开通一下」代替；
- 必要时**一次只给一步**，等用户回复再进行下一步；
- 用户把钥匙发来后，**只用于当前这一次配置**，不写入任何文件、不落库、不回显完整内容（见安全约定）。

### 0.3 帮用户配置麦当劳 MCP

拿到 Token 后，智能体**代替用户完成配置**：

- 在**宿主平台的连接器 / MCP 设置**中，新增一个名为 `mcd-mcp` 的 MCP Server，
  按下方内容填写（把 `{用户提供的 Token}` 换成实际 Token）：
  ```json
  {
    "mcpServers": {
      "mcd-mcp": {
        "type": "streamablehttp",
        "url": "https://mcp.mcd.cn",
        "headers": { "Authorization": "Bearer {用户提供的 Token}" }
      }
    }
  }
  ```
- 若平台支持通过对话/工具自动写配置，**直接帮用户写好并启用**；
- 若平台配置必须由用户手动操作（如某个设置页面），则**给出逐字段的填写指引**
  （告诉用户每个框填什么，越具体越好）。

### 0.4 验证配置是否成功

配置后**立即验证**：调用一个麦当劳 MCP 工具（如 `now-time-info` 或 `query-meals`）。

- **成功** → 用大白话报喜：「开通好啦！我刚刚试了一下，能正常查到麦当劳的东西了 🎉」；
- **失败** → 别甩错误码，翻译成人话再给一步操作：
  - 钥匙不对 / 过期（`401`）→ 「这把钥匙好像不太好使，咱们回上一步重新拿一把试试～」；
  - 没找到麦当劳工具（连接器没启用）→ 「我还没接通上，你那边是不是有个『保存』或『启用』
    没点？点一下再试试」；
  - 网络问题 → 「我这边网络好像没连上，你稍等我再试一次，或者你看看网有没有断」。

### 0.5 引导用户创建第一个订阅

开通成功后，**顺势**问用户想盯什么，别冷场：

> 「好啦，现在你想让我帮你盯着啥？随便挑，也可以都选：
> ① 某一款套餐（比如巨无霸套餐）；
> ② 有新品就告诉你；
> ③ 有优惠券就提醒你——**也可以让我顺手自动帮你领**，你说了算；
> ④ 某个城市搞活动了告诉你。
>
> 另外，你想让我多久帮你看一眼？不挑的话我默认每天中午和半夜各看一次～」

然后把用户的回答交给「场景 A」，自动完成订阅 + 定时任务创建。

## 二、场景 A：用户要订阅

### 触发

用户说类似：

> 「帮我订阅巨无霸套餐，有优惠或降价就发到我邮箱 xxx@example.com」
> 「出新品就通知我」「有咖啡券叫我」「上海有新活动告诉我」「30 元以内降价提醒我」

### 智能体要做的事

**第 1 步：解析订阅意图**，从自然语言中提取：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| `label` | 订阅名称（用于邮件标题、任务名） | 「巨无霸套餐」「任意新品」 |
| `keywords` | 匹配关键字（命中餐品名/活动名/券名） | `巨无霸`、`新品`、`咖啡` |
| `email` | 推送邮箱（**必须向用户确认**） | `me@qq.com` |
| `watches` | 关注维度（可多选，默认全开） | `new_item price_drop` |
| `auto_claim` | **是否自动领券**（默认**关**；用户明确说要才开） | `true` / `false` |
| `schedule` | **检查频率（由用户决定，默认 12:00 + 24:00）** | `每天12点`、`每3小时`、`只晚上8点` |
| `city` | 城市（可选，用于活动过滤） | `上海` |
| `max_price` | 价格上限（可选，用于降价过滤） | `40` |

`watches` 取值：

- `new_item` → 新品 / 新套餐（`query-meals`）
- `price_drop` → 降价（`query-meals` + 价格快照比对）
- `new_coupon` → 新优惠券（`available-coupons` / `query-my-coupons` / `query-store-coupons`）
- `campaign` → 营销活动（`campaign-calendar`）

### 自动领券（`auto_claim`）

**默认关闭**——因为领券是**写操作**（会改变账户券包状态），须经用户明确同意才开启：
用户说「**自动帮我领券**」「**能领的券顺手领了**」「**有券自动领**」时才置 `true`。

开启后，**每次定时检查时**（与订阅检查同一趟执行，不额外建任务）：

1. 先调 `available-coupons` 取出当前可领券清单；
2. **按订阅的 `keywords` 筛选**出落在关注范围内的券（如订阅「咖啡」→ 只认含"咖啡"的券）；
3. **若范围内存在可领券** → 调 `auto-bind-coupons` 领取；
4. **如实告知**：领完在邮件里列出本次领到的券名。
   注意该工具为「**一键领取全部可用券**」，会领到范围外的券也在所难免——
   所以通知中要写清「本次实际领取了：…（含自动领取的全部可用券）」，**不要谎称只领了范围内的**；
5. 若范围内**没有**可领券，则**不调用** `auto-bind-coupons`，静默跳过（避免无谓的账户变动）；
6. 领券失败（限流/过期）**不阻断**订阅检查主流程，只在邮件里附一句"本次有券未能领取"。

> `auto_claim` 是否开启，同样**需向用户复述确认**（如「以后有咖啡券我会自动帮你领，可以吗？」）。

### 频率（`schedule`）由用户输入决定

**默认**为每天 **12:00 与 24:00** 两次；但**用户怎么说，就怎么设**。
智能体需把用户的自然语言时间表达翻译成具体的触发时间点。

| 用户怎么说 | 解析为触发时间 | 说明 |
| --- | --- | --- |
| （未提时间，默认） | 每天 12:00、24:00 | 覆盖午市 + 夜间上新 |
| 「一天一次」「每天一次」 | 每天 12:00 | |
| 「一天两次」「每天两次」 | 每天 12:00、24:00 | 等同默认 |
| 「早上 8 点」「每天 8:00」 | 每天 08:00 | |
| 「12 点和 24 点」 | 每天 12:00、24:00 | 显式指定 |
| 「只晚上提醒」「晚上 8 点看一次」 | 每天 20:00 | 单点 |
| 「每 3 小时」「每两小时」 | 00:00 起每 3h / 每 2h | 按间隔铺开 24 小时 |
| 「工作日提醒」 | 周一至周五 12:00 | 排除周末 |
| 「只在饭点」 | 每天 11:30、17:30 | 理解为用餐前 |
| 「每小时」 | 每小时整点 | 提示用户可能偏频繁 |

**规则**：

- 时间一律按**用户所在时区**（即宿主平台当前时区）理解；
- 解析后**必须向用户复述**确认，例如「将每天 12:00 与 24:00 检查，可以吗？」；
- 若用户表达模糊（如「经常」），**默认 12:00 + 24:00** 并说明；
- 若用户要求**高频（＜1 小时/次）**，提醒「优惠活动按天更新，过频没有收益」，
  但仍尊重用户选择；
- `schedule` 会写入定时任务的触发时间，**用户之后随时可以改**（见场景 D）。

**第 2 步：向用户复述订阅内容、邮箱与检查频率**（邮箱是外发动作，必须确认）。

**第 3 步：创建一条宿主平台的定时任务**，触发时间采用解析出的 `schedule`
（用户没指定则默认 **12:00 + 24:00**）。

> 不同平台的定时任务机制不同（WorkBuddy 的「自动化任务」、Hermes 的定时任务、
> 通用 Cron 等），**按其平台的原生方式创建即可**，本 skill 不限定具体实现。
> 任务内容 = 一段给未来的智能体看的指令，说明「检查什么、用什么工具、命中后发邮件给谁」。

任务指令模板（把 `{...}` 换成实际值）：

```text
【麦当劳订阅雷达 · 定时检查】
订阅名称：{label}
推送邮箱：{email}
检查频率：{schedule}          # 如「每天 12:00、24:00」；由用户决定
关注维度：{watches}
匹配关键字：{keywords}
自动领券：{auto_claim}         # true / false（默认 false）；开启后检查时顺带领券
城市：{city}
价格上限：{max_price}

请执行：
1. 调用麦当劳 MCP 工具获取最新数据：
   - 若关注 new_item / price_drop → 调 query-meals（必要时 query-meal-detail）
   - 若关注 new_coupon → 调 available-coupons、query-my-coupons（有门店则加 query-store-coupons）
   - 若关注 campaign → 调 campaign-calendar
   - 【自动领券】若 {auto_claim}=true → 额外执行自动领券流程（见下）
2. 若需要判断时效 → 调 now-time-info；需要核价 → calculate-price
3. 按「匹配关键字 / 价格上限」筛选出与订阅相关的条目
4. 与上次检查结果比对，只保留【新增或发生变化】的条目（新品、降价、新券、新活动）
5. 【自动领券】当 {auto_claim}=true 时：
   a) available-coupons 取出可领券清单
   b) 按 {keywords} 筛出落在订阅范围内的可领券
   c) 范围内有可领券 → auto-bind-coupons 领取；无则不调，静默跳过
   d) 领券失败不阻断本流程，仅在邮件中附注
   e) ⚠️ auto-bind-coupons 为「一键领取全部可用券」，通知中须如实列出【本次实际领取的券】，
      不要谎称只领了订阅范围内的
6. 若有新变化（含本次新领到的券）：整理成简洁中文摘要，发送邮件到 {email}，
   主题：【麦当劳订阅雷达】{label} 有 N 条新动态
   若没有新变化且未领到新券：不发邮件，静默结束
```

**第 4 步：告知用户订阅已生效**，说明「按你设定的 {schedule} 自动检查，有新动态才发邮件，
频率随时可改」。

## 三、场景 B：用户想立刻查一次（或立刻领一次券）

用户说「现在巨无霸套餐多少钱？」「最近有什么新品券？」时，
**直接调用 MCP 工具**取数并回答，不必创建定时任务：

1. 按问题选择工具（菜单 → `query-meals`；券 → `available-coupons`/`query-my-coupons`；活动 → `campaign-calendar`）；
2. 必要时用 `query-meal-detail` 补充套餐组成、`calculate-price` 核对到手价、`now-time-info` 判断时效；
3. 用清晰的中文表格或列表回答，并注明「以麦当劳官方实时结果为准」。

用户说「**现在有什么券，帮我领了**」「**把能领的券都领一下**」时——
这是**即时的领券请求**（与订阅无关，用户当场授权、当场执行）：

1. 先调 `available-coupons` 列出当前可领的券给用户看；
2. 用户确认要领 → 调 `auto-bind-coupons` 执行（注意该工具为**一键领取全部可用券**，
   领取后**如实告知**实际领到的券）；
3. 领完可用 `query-my-coupons` 展示券包现状，方便用户核对。

> 即时领券是一次性授权、当场完成，不会留下任何定时任务。

## 四、场景 C：定时任务触发

定时任务按**用户设定的 `schedule`** 唤醒智能体（默认每日 12:00 / 24:00），
智能体按任务指令里的步骤执行（见场景 A 第 3 步模板）。
要点：

- **只推变化**：与上次检查比对，没有新变化就**不发邮件**，避免打扰；
- **降价的判定**：需要对比上次价格。可在任务指令里提示智能体
  「若记忆中/上次结果里有该餐品价格，则与其对比；首次检查只记录，不报降价」；
- **限流意识**：麦当劳 MCP 限流 600 次/分钟。常规频率下调用量极低，无需担心；
  即使用户设了较高频率，也应在每次检查内**只调必要的工具**。

## 五、场景 D：用户要修改订阅（含改频率）

用户可以随时调整已有订阅，常见改动：

| 用户说 | 智能体的动作 |
| --- | --- |
| 「改成每天一次」 | 更新对应定时任务的触发时间为每天 12:00 |
| 「以后只在晚上 8 点提醒」 | 改为每天 20:00 |
| 「每 2 小时检查一次」 | 改为每 2 小时触发（并提醒频率偏高） |
| 「换一个邮箱，发到 xx@yy.com」 | 更新任务指令中的推送邮箱 |
| 「巨无霸那个别推降价了，只要新品」 | 更新 `watches`，去掉 `price_drop` |
| 「先停掉」/「删掉这个订阅」 | 停用/删除对应定时任务 |

3. 改完**复述新频率**给用户确认；
4. 若用户说的是相对表达（「调低一点」「勤快一点」），
   基于当前频率给出**具体建议**（如「从每天两次改为每天一次，可以吗？」）。

## 六、场景 E：定时点餐

除了「提醒优惠」，本 skill 还支持**定时自动点餐**：
用户设定「到点帮我下好单」，到点智能体自动选好固定套餐、生成订单，
把**付款入口（麦当劳 App 链接）**推给用户，用户在**自己的麦当劳 App 里**完成付款。

> **周期与时间必须由用户主动给出**：工作日、**每天、指定星期几、每月某几天、
> 一次性（某天某点）、甚至每 N 天**都可以，但**用户没说清就问，绝不替他默认**——
> 每天自动建单又没人付款，反而给用户添麻烦。各类周期全部走**同一套下单逻辑**，
> 差异只在「什么时候触发」，触发后的执行流程完全一致。

> ⚠️ **铁律：绝不自动付款。** 本 skill 只做到「生成订单 + 给出付款入口」，
> **永远不代替用户完成支付**。钱由用户在自己的麦当劳 App 里确认。
>
> 📱 **付款入口 = 麦当劳 App 链接**：`create-order` 返回的支付链接，本质是
> 「**打开 / 唤起麦当劳 App**」的链接——用户点开后即在**麦当劳 App 内**完成付款，
> 无需在陌生网页输入任何支付信息。推送时要**讲清这一点**，让用户放心点。

> ⚡ **每次下单前都查券比价**：穷尽当前所有可用券，挑**实际到手价最低**的那张，争取最省。
> 🔒 **外送必须有地址**：没有收货地址时**先让用户填写**，地址未补齐不下单。

### 触发

用户说类似：

> 「**工作日**每天中午 12 点帮我点一份巨无霸套餐，外送到公司」　　　← 工作日周期
> 「**每天**早上 8 点帮我下个大杯咖啡，我到店自取」　　　　　　　　← 每天周期
> 「**每周一、三、五**中午帮我订个沙拉，送到公司」　　　　　　　　← 指定星期几
> 「**每个月 1 号**中午给我来份新品套餐」　　　　　　　　　　　　　← 每月固定日
> 「**明天中午 12 点**帮我点一份巨无霸套餐」（一次性）　　　　　　← 单次
> 「订个工作餐，中午自动下好单，链接发我微信/邮箱」

### 需要问清的要素

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| `meal` | 固定套餐（含餐品编码或名称 + 可选规格） | 巨无霸套餐（中薯中可） |
| `order_schedule` | **点餐周期**（何时触发，见下表）；**必须由用户明确说出，未说就问，不得默认** | 工作日 / 每天 / 每周一三五 / 每月1号 / 仅明天 |
| `order_time` | 触发日几点下单（是"下单时间"，不是"取餐时间"）；**必须由用户明确给出，不得默认取某个时间** | 11:30（留 30 分钟给取餐） |
| `mode` | 就餐方式：`delivery`（外送）/ `pickup`（到店取餐） | delivery |
| `address` | **外送时必填**的收货地址；用户没有时必须先让用户填写，**否则不下单** | 公司地址 |
| `store` | 到店取餐时的门店 + 取餐时间 | 附近门店，12:00 取 |
| `notify_to` | 付款入口（麦当劳 App 链接）发到哪（邮箱必填，可另加平台内推送） | me@qq.com |

**`order_schedule`（点餐周期）取值与解析**：

| 用户怎么说 | 解析为触发周期 | 备注 |
| --- | --- | --- |
| 「工作日」「周一到周五」 | 周一至周五 | |
| 「每天」「天天」 | 每天 | |
| 「每周一三五」「每周一、三、五」 | 周一、周三、周五 | 任意星期组合 |
| 「每周末」 | 周六、周日 | |
| 「每月 1 号」「每月 1 号和 15 号」 | 每月 1 日 / 每月 1、15 日 | 多日可用逗号分隔 |
| 「每 2 天」「每隔一天」 | 每 2 天一次（从明天起） | 按间隔铺开 |
| 「明天中午」「就这一次」「仅 10 月 15 日」 | 一次性：指定日期 + 时间 | 触发一次后任务自动结束 |

> 规则：**周期与下单时间必须由用户主动给出——用户没说就问，绝不默认**（自动每天建单
> 却无人付款，是给用户添堵）；周期解析后**必须向用户复述确认**（如「每周一、三、五 11:30 帮你下单，对吗？」）；
> 周期越特殊越要确认清楚，避免误下单。用户随时可改周期（见场景 D「修改订阅」同思路）。

### 智能体要做的事

**第 1 步：配置阶段（一次性）** —— 帮用户把点餐前提准备好：

- **外送**：
  1. 调 `delivery-query-addresses` 取用户已有地址列表；
  2. **有地址** → 与用户确认用哪一个（多个时让用户选，不要替他决定），固化为 `address`；
  3. **无地址** → ⚠️ **必须先让用户填写完整收货地址**（联系人、手机号、省市区、详细门牌），
     再用 `delivery-create-address` 新增，**地址未补齐前不得创建该外送定时任务**；
     话术示例：「外送得先有个收货地址哈～你告诉我送到哪儿：联系人 + 手机号 + 详细地址（比如 上海市浦东新区张江路 100 号 3 号楼 502），我帮你记上。」
  4. 地址就绪后，调 `delivery-query-stores` 找到可配送门店并记录门店编码；
- **到店取餐**：调 `query-nearby-stores` 找到目标门店，记录门店编码与取餐时间；
- **确认套餐**：调 `query-meals` 找到该套餐的 `mealCode`，
  `query-meal-detail` 确认套餐组成与可选规格（如饮料换成无糖），用户确认后固化为 `meal`。

> 🔒 **外送地址是硬门槛**：`mode=delivery` 且地址缺失时，**任务不得建立、订单不得创建**。
> 宁可停下来问用户，也不要用一个猜测的地址下单。

**第 2 步：创建定时点餐任务** —— 触发时间用 `order_schedule` + `order_time`
（如「每周一至周五 11:30」「每天 08:00」「每月 1 日 12:00」「2026-10-15 12:00 一次性」），
任务指令模板见下。

**第 3 步：任务触发时的执行逻辑（智能体按指令逐步做，各类周期完全一致）**：

1. 先用 `now-time-info` 确认今天确实命中 `order_schedule`（工作日 / 指定星期几 /
   每月某日 / 一次性日期等）、且已到 `order_time`；**不命中或时间未到则静默结束**；
2. `query-meals` 拉最新菜单，确认目标套餐仍在售（下架/改名要如实告知）；
3. **⚡ 下单前必查优惠券，争取最低价（每次下单都要做，不可跳过）**：
   1. **穷尽可用券**：`available-coupons`（可领/可用活动券）、`query-my-coupons`（账户已有券）
      都要查；若已知门店，**再加** `query-store-coupons`（该门店专属券）；
   2. **逐张比价**：把每张券对目标 `meal` 用 `calculate-price`
      试算一遍，**横向对比所有组合的到手价**（券后价 + 配送费 − 满减），
      选出**实际支付最低**的那一张（注意：面额大的券未必最省，可能有门槛或限品类）；
   3. **自动领券**：若最优券尚未领取但可领，先领再算（如 `available-coupons` 中标记可领的）；
   4. **没有可用券也用原价下单**，不要因无券而卡住；
   5. **记录结论**：最终采用哪张券、省了多少钱，用于告知用户（见第 5 条）。
4. `calculate-price` 复核最终金额（餐品 + 配送费 − 最优券优惠），
   与第 3 条比价结论一致才继续；
5. **⚠️ 地址兜底校验（外送场景）**：若 `mode=delivery`，下单前再次确认收货地址有效
   （地址仍在 `delivery-query-addresses` 列表中、且门店可配送）；
   **地址缺失或失效 → 立即中止下单**，改为发通知请用户补填地址，**绝不臆造地址下单**；
6. **`create-order`** 创建订单（带上门店/地址/就餐方式/商品列表/取餐时间/所用券）；
7. 拿到订单详情与**付款入口**后，**推送给你**：主题如
   「【麦当劳已下单】巨无霸套餐 ¥32.5，已用〔立减5元券〕省 5 元，请到麦当劳 App 付款 → {App 链接}」，
   并说明「点开链接会**打开麦当劳 App**，在里面完成付款；订单 X 分钟内有效，逾期自动取消」；
8. **到此为止，绝不代付**。若用户没付款，订单自然过期，不重复催单。

**第 4 步（可选）：下单后跟进** —— 用户付款后，可用 `query-order` 查订单状态；
用户说「今天不想吃了」可 `cancel-order` 取消。

### 定时点餐任务指令模板

```text
【麦当劳订阅雷达 · 定时点餐】
点餐内容：{meal}                 # 如 巨无霸套餐（中薯中可）
点餐周期：{order_schedule}       # 工作日 / 每天 / 每周一三五 / 每月1号 / 仅2026-10-15
下单时间：{order_time}           # 如 11:30
就餐方式：{mode}                 # delivery 外送 / pickup 到店取餐
配送地址/门店：{address_or_store}
取餐时间（到店时）：{pickup_time}
付款入口推送到：{notify_to}

请执行：
1. now-time-info 确认今天是否命中【点餐周期 {order_schedule}】、且已到 {order_time}；
   不命中或时间未到则静默结束（一次性任务触发完成后再无后续）
2. query-meals 确认 {meal} 仍在售（下架/改名则发通知告知，不强行下单）
3. 【必做】下单前查优惠券争取最低价：
   a) 查可用券：available-coupons + query-my-coupons（已知门店则加 query-store-coupons）
   b) 逐张用 calculate-price 试算，选出【实际到手价最低】的券（面额大不等于最省）
   c) 最优券若可领未领，先领再算
   d) 无可用券则按原价继续，不因无券卡住
4. 【外送必做】校验收货地址：delivery-query-addresses 确认 {address_or_store} 有效；
   地址缺失或失效 → 中止下单并发通知请用户补填，绝不臆造地址
5. calculate-price 复核最终金额（餐品 + 配送费 − 最优券）
6. create-order 创建订单（门店/地址/就餐方式/商品列表/取餐时间/所用券）
7. 取得付款入口后，推送到 {notify_to}，主题：
   【麦当劳已下单】{meal} ¥{金额}，已用〔{券名}〕省 {省额} 元，请到麦当劳 App 付款 → {App 链接}
   并注明：① 点开链接会打开麦当劳 App，在 App 内完成付款；
          ② 订单有效期（逾期自动取消）
8. ⚠️ 绝不代替用户支付；不重复催单
```

### 安全与合规红线（务必遵守）

- **绝不自动扣款 / 代付**：只生成订单与付款入口，付款必须由用户本人在**自己的麦当劳 App 内**完成；
- **⚡ 下单前必查券比价**：每次下单都要查遍可用券（`available-coupons` +
  `query-my-coupons` + 门店券），逐张试算取**实际到手价最低**的方案，
  不许"有券就用第一张"或直接原价下单（仅在确实无可用券时才用原价）；
- **🔒 外送必须有地址**：`delivery` 模式下，地址缺失或失效时**必须中止下单**并请用户补填，
  **绝不臆造、绝不猜测、绝不用旧地址硬下**；
- **金额与内容先核对再下单**：下单前用 `calculate-price` 复核，避免价格异常时误下单；
- **套餐不存在时不下单**：若目标套餐下架，只发通知、不自作主张换其他套餐；
- **一键可停**：用户说「停掉某个点餐」/「停掉工作日点餐」应能立即停用对应任务
  （不区分周期，任何 `order_schedule` 的任务都要能一键停）；
- **一次性任务不留残**：`order_schedule` 为一次性时，触发并下单后任务即视为完成，
  不再重复触发；
- **付款入口属敏感信息**：只推送到用户本人确认的渠道，不外泄；
  推送时**要讲清"点开即打开麦当劳 App 付款"**，让用户明白这是官方 App 入口、可放心点。

## 八、注意事项

- **把用户当小白**：默认用户不懂 Token / MCP / 定时任务，要用大白话分步引导，
  能代做的（如写配置）就代做，必须用户做的（如申请 Token）就手把手教；
- **邮箱必须由用户提供并确认**，智能体不得臆造收件地址；
- **频率以用户输入为准**，默认 12:00 + 24:00，可随时修改；改动后需复述确认；
- **凭证不落库**：Token 仅用于当次配置，**不写入任何文件、不回显完整 Token**；
  长期由宿主平台的连接器统一管理，本 skill 不接触、不存储；
- **自动领券须用户授权**：`auto_claim` **默认关闭**，领券是**写操作**（改变账户券包），
  必须用户明确同意才开启；领券范围**以订阅关键字为界**，无范围内可领券时不调用领取接口；
  由于 `auto-bind-coupons` 是「一键领取全部可用券」，通知中**须如实列出实际领到的券**，
  不得误导用户以为只领了订阅范围内的；
- **绝不自动付款（红线）**：涉及点餐时，只做到「生成订单 + 给出付款入口（麦当劳 App 链接）」，
  **永远不代替用户完成支付**；付款在**用户自己的麦当劳 App 内**完成，推送时须说明这一点；
  下单前**必查所有可用券并比价取最低**；
  外送**地址缺失即中止下单**、先请用户填写（绝不臆造地址）；下单前必须核价、套餐下架不得擅自替换；
- **点餐周期与时间必须用户主动给出**：**每天 / 指定星期几 / 每月某日 / 一次性**等
  都支持且走同一套下单逻辑；但用户没说清就问，**绝不默认周期、绝不默认下单时间**
  （避免每天自动建单无人付款）；周期解析后必须复述确认；
- **合规**：所有输出标注「以麦当劳官方实时结果为准」，并说明本项目为
  麦当劳程序员节创意开发大赛参赛作品，非麦当劳官方产品；
- **可被组合调用**：其他技能可把「订阅/查询麦当劳优惠」的意图直接路由到本 skill。

## 九、最小示例（对话视角）

### 示例 1：小白首次使用（含引导配置）

```text
用户：我想让它帮我盯麦当劳的优惠

智能体（静默探测 → 发现还没接通）：
  「好嘞～不过得先让麦当劳官方给咱们一把『钥匙』，有了它我才能帮你查菜单和优惠。
   很简单，照着点几下，1 分钟就好，我在这儿等你：
   ① 打开 https://open.mcd.cn/mcp/doc
   ② 点右上角『登录』，填手机号收个验证码登进去
   ③ 右上角会变成『控制台』，点它，再点『激活』
   ④ 弹出来让同意协议，点『同意』
   ⑤ 看到一大串字母数字，那就是钥匙——点『复制』，直接发给我就行～」

用户：（照着做，把钥匙发来）

智能体：
  ① 默默帮你配好（钥匙只在这次用一下，不存下来）
  ② 试了一下，能查到麦当劳的东西 → 「开通好啦！🎉」
  ③ 「那你想让我帮你盯着啥？某个套餐 / 有新品 / 有券 / 某城市活动，随便挑，
     也可以都选。多久看一次也你说了算，不挑就默认每天中午和半夜各一次～」
  ④（用户选择后）→ 走「场景 A」完成订阅与定时任务

用户：盯巨无霸套餐，有新品或降价就发我邮箱 me@qq.com

智能体：搞定！以后每天中午 12 点和半夜 12 点我帮你看一眼，有新品或者降价就发邮件告诉你 ✅
```

```text
用户：帮我盯着咖啡的券，有券自动领了，发我邮箱 me@qq.com，每天中午看一次

  ③ 用户确认 → 创建定时任务（指令含「自动领券：true」）

（某天 12:00 触发）

  available-coupons → 查出可领券：〔咖啡买一送一〕〔巨无霸立减5元〕〔早餐粥减3元〕
  → 按 keywords=[咖啡] 筛选 → 范围内有〔咖啡买一送一〕可领 ✅
  → auto-bind-coupons 执行领取
  → 发邮件：「【麦当劳订阅雷达】咖啡券 有 1 条新动态
            已为你自动领取：〔咖啡买一送一〕

        → 无新变化 → 不发邮件，静默结束 ✅

```

### 示例 3：定时点餐 · 工作日周期（含比价选券 + 外送地址校验）

```text
用户：工作日每天中午 12 点帮我点一份巨无霸套餐，外送到公司

智能体：
  ① 问清要素：套餐=巨无霸套餐（中薯中可）、周期=工作日（周一~周五）、
            下单时间=11:30（提前 30 分钟）、方式=外送
  ② 查地址：delivery-query-addresses → 发现没有可用地址
     → ⚠️「外送得先有个收货地址哈～你告诉我送到哪儿：联系人 + 手机号 +
        详细地址，我帮你记上。」
  ③ 用户提供后 → delivery-create-address 新增 → delivery-query-stores 找门店
  ④ 确认套餐：query-meals 找到 mealCode，query-meal-detail 确认规格
  ⑤ 复述确认：「每周一到周五 11:30，帮你在〔XX门店〕下巨无霸套餐，外送到你填的地址，
             每次下单前我会自动挑最划算的券，下单后把麦当劳 App 付款链接发你邮箱，
             你点开在 App 里付——可以吗？」
  ⑥ 用户确认 → 创建定时点餐任务（周期=周一~五，11:30）

（某工作日 11:30 触发）
智能体：
  now-time-info 确认命中「工作日」周期 → query-meals 确认套餐在售 →
  【比价选券】available-coupons 查出「满30减5」「麦麦省9折」，
            query-my-coupons 查出「新客立减8元」，门店券查出「指定套餐减4元」
            → 逐张 calculate-price 试算：
               满30减5 → ¥35.5   /   9折 → ¥36.0
               新客减8 → ¥32.5   /   门店减4 → ¥36.5
            → 选出最低：新客立减8元，到手 ¥32.5
  → 外送地址校验：delivery-query-addresses 确认地址仍有效 ✅
  → create-order（带券）→ 拿到付款入口（麦当劳 App 链接）→
  发邮件：「【麦当劳已下单】巨无霸套餐 ¥32.5，已用〔新客立减8元券〕省 8 元，
          请到麦当劳 App 付款 → {App 链接}（点开即打开麦当劳 App；订单 15 分钟内有效）」

用户：（点链接打开麦当劳 App，在 App 内自行付款）→ 完成 ✅
（智能体绝不代付；用户若没付款，订单自然过期，不重复催单）
```

### 示例 4：定时点餐 · 其他周期（同一套逻辑）

```text
用户：每周一、三、五早上 8 点给我来个大杯咖啡，我到公司楼下取

智能体：
  ① 问清要素：套餐=大杯咖啡、周期=周一·周三·周五（非工作日周期！）、
            下单时间=08:00、方式=到店取餐
  ② 查门店：query-nearby-stores 找到「公司楼下门店」，记录门店编码 + 取餐时间
  ③ 确认套餐：query-meals 找到大杯咖啡 mealCode
  ④ 复述确认：「每周一、三、五 08:00，在〔公司楼下门店〕帮你下大杯咖啡到店取，
             每周执行 3 次，下单前自动比价选券，麦当劳 App 付款链接发你邮箱——可以吗？」
  ⑤ 用户确认 → 创建定时点餐任务（周期=每周一三五，08:00）

（某周一 08:00 触发）
  now-time-info 确认命中「周一」→ 后续流程与示例 3 完全一致：
  确认套餐在售 → 比价选券 → 到店场景无需地址校验 → 核价 → create-order
  → 推送付款入口（麦当劳 App 链接）

（某周二 08:00，任务照常唤醒）
  now-time-info 确认今天不是周一三五 → 不命中周期 → 静默结束，不下单、不打扰 ✅
```

### 示例 5：外送但没地址 → 必须让用户填

```text
用户：帮我定个午餐，巨无霸套餐，外送到我家

智能体：
  ① delivery-query-addresses → 用户账户下没有已保存地址
  ② ⚠️ 触发地址门槛：不下单、不建任务，先向用户索要完整地址
     「外送必须有收货地址才能下单～麻烦给我：联系人、手机号、
      和详细地址（省市区 + 街道门牌），我帮你存下来，以后就不用再填啦。」
  ③ 用户填写 → delivery-create-address 新增成功 → 继续后续配置
```

> 若用户始终不提供地址，则该外送点餐**无法建立**——智能体会说明原因，
> 并建议改用「到店取餐」作为替代方案。
