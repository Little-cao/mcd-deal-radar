# 关于「主动推送」与调用量

这份文档回答两个关键问题：

1. 有没有办法让**麦当劳主动推送**消息给用户？
2. 每天定时去查，会不会消耗大量 token / 撑爆 MCP 调用量？

---

## 一、结论先说

| 问题 | 答案 |
| --- | --- |
| 麦当劳 MCP 有 webhook / 订阅回调吗？ | **没有。** 官方 30+ 个 Tool 全是「查询类」，只能拉，不能推。 |
| 那怎么实现「主动收到推送」？ | 用**定时任务周期拉取**，检测到变化就发邮件——体验上就是「主动推送」。 |
| 会很费 token 吗？ | 一天只唤醒 2 次（12:00 / 24:00），每次几条 MCP 调用，成本极低。 |

---

## 二、为什么麦当劳 MCP 没有「推」

麦当劳 MCP Server（<https://mcp.mcd.cn>）提供的全部是可主动调用的查询/下单工具，
例如 `query-meals`、`available-coupons`、`campaign-calendar` 等，
**没有** `subscribe` / `webhook` / `push` / `notify` 这类订阅式接口。

这是 MCP 作为「工具调用协议」的常见形态：**Client 主动调，Server 被动答**。
所以「让麦当劳主动联系你」在协议层面做不到，只能靠定时拉取。

---

## 三、为什么这是「低成本」的

本 skill 的设计把成本压到很低，且**频率由用户自己掌控**：

1. **频率可调**：默认 **12:00 与 24:00** 两个触发点，共 2 次；
   用户也可改为每天一次、早上 8 点、每 3 小时等——**你设多少就查多少**；
2. **按需调用**：只调用订阅关注维度对应的工具。
   例如「只看优惠券」的订阅只调 `available-coupons` + `query-my-coupons`，
   不会去调菜单和活动接口；
3. **只推变化**：与上次结果比对后，**没有新变化就不发邮件、不打扰**；
4. **不造轮子**：取数直接用宿主平台已接入的麦当劳 MCP，无需自建脚本与 Token 管理。

对比「agent 每隔几分钟就轮询一次」的做法，本 skill 的调用量在**默认频率**下低了数个数量级；
即便用户主动调高频率，也仍是用户知情下的自主选择。

---

## 四、调用量估算

以**默认频率**（每天 2 次）、5 条订阅、每条 2~4 次 MCP 调用估算：

| 指标 | 数值 |
| --- | --- |
| 每日 MCP 调用次数 | 约 20~40 次 |
| 官方限流上限 | 600 次/**分钟** |
| 结论 | 距离上限极远，完全无需担心 |

> 用户若把频率调高（如每 3 小时 → 每天 8 次），调用量仍远低于上限。

---

## 五、实操建议

1. **默认 12:00 / 24:00 两次**对多数人足够；想更省可设为每天一次，
   想更及时可设为早上 8 点等——**频率由用户输入决定**；
2. **让定时任务唤醒智能体去调 MCP**，这正是本 skill 的设计——
   取数交给智能体 + MCP 工具，而不是写死一个脚本；
3. **想扩场景**，用一个新订阅表达即可，例如：
   - 「新品一出就告诉我」→ 关注维度含 `new_item campaign`
   - 「有便宜券就叫我」→ 关注 `new_coupon`
   - 「降到 30 以下提醒我」→ 价格上限 30 + 关注 `price_drop`

详见同目录 `scheduled-task.md`。
